Identity / source

Keep the facts with the project.

.project.json is the project's identity record. Its project_id is the stable machine name, while project_name is what people read. A renamed “Studio Notes” can still be studio-notes. A board binding can be added later; none is required to give this project an identity.

FICTIONAL EXAMPLE · .project.jsonNO BOARD / NO AGENT
{
  "project_id": "studio-notes",
  "project_name": "Studio Notes",
  "agents": {}
}

The registry stores an index of known manifests, including their locations and derived facts, in PostgreSQL. It is not another editable project definition, a source-code repository, a ticket board, or an agent roster. The file wins; the directory can be rebuilt from registered files.

Discovery / index

Registration makes a project findable.

  1. Write or adopt the manifest.It lives with the project; PJangler can prepare one through pj init.
  2. Register or refresh it.pj reindex indexes the current project. The service needs access to the manifest's file location.
  3. Read the result.pj list shows indexed projects; pj info and pj doctor explain this one's identity and health.
A directory, not a search party. Refreshing the registry revisits known file paths. It does not scan the whole filesystem for new projects. Registration also does not prove that a linked ticket board was contacted; provider verification is a separate operation.

A project may have no Git history, ticket board, or hired agent. Those are separate choices.

Preparation / conventions

A starter, not a takeover.

CommonProject is a versioned starter template vendored by PJangler. Copier renders a baseline of project files from it. pj init can create a new project or adopt an existing one; it previews by default, and pj init --apply writes the proposed setup. By default, applying init also creates or links a ticket board; choose --skip-board explicitly for a boardless project like Studio Notes. That prepares a project—it does not certify that the project has passed acceptance on another machine.

Existing projects can bring in conventions selectively. A subsystem recipe adds a capability; an audit checks how the project compares with the shared standard; a targeted migration changes one known point of drift. Review proposed changes and preserve files the project already owns. The template is the upstream starting point; rendered files belong to the project.

Optional detail / command desk

What you might ask someone to show you.

Examples, not buttons that run anything. These assume PJangler is installed; registry-wide lookups need its service available. Run project-local commands from the relevant project directory.

Change / two meanings

“Migration” can mean two different jobs.

Bring a project up to standard

Audit, preview a targeted rule with pj migrate <rule> --dry-run, inspect the proposed changes, then run pj migrate <rule> only if approved. Audit again afterward. There is no --apply flag for pj migrate. Back up or commit your existing changes first; rollback is not a universal guarantee.

Import an old registry

A historical one-way import moves discovery from legacy YAML to canonical manifests and the service index. Manifest facts win over old records. The importer records file locations and hashes in a receipt and does not write ticket boards. This is a transition task, not daily project maintenance.

Boundaries / fleet

Project identity is not an org chart.

PJangler knows the project and its board binding. Flume hires and provisions employees and owns the agent roster; Hermes runs an agent. The agents field in a project's manifest is a one-way projection of the Flume-owned org chart, not an invitation to edit staffing there.

FLEET AUTHORITYFlume org chart → agent profile

Momo is the PM playbook, Pilot (px) talks to boards, and Krebs executes within enrollment. Candystore history, Hindsight recall and Holocene displays can use shared project identity where integrated. The core NATS bus, PostgreSQL, ntfy and voice services can operate without this index: shared identity is not a power switch for every service.

Field note / keep this

What you can now explain.

The project file is the source. The registry is its rebuildable directory. CommonProject prepares a baseline; audit and migration keep it aligned. Flume—not PJangler—hires the people who work on it.

When the registry is accepted on your setup, ask Rererere to show you pj list. Seeing a project there means it was indexed; it does not by itself prove the board or an agent is ready.
