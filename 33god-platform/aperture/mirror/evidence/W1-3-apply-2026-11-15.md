## Root cause the menu did not know: the "no recorded project" failures were a device-id drift

The menu blamed missing receipts. Receipts existed. Skillex records `dev` + `ino` + link text for every entry it owns (`src/core/activation-ownership.ts`, `matches()` requires `dev` equality). After the 2026-11-14 ~20:29 EST restart the Data volume's device number on the Mac changed from `16777233` to `16777234`. Every receipt then read as "ownership changed" (`E_OWNERSHIP_CHANGED` global, `E_PROFILE_ROOT_CHANGED` desks), `sync` and `profile sync` refused before planning anything, and the resync saw all six desks as errors. The old BMAD `E_SKILL_MISSING` was a second, separate problem.

Repair done (Skillex has no supported command for it; `migrate` and `root adopt` do not cover device renumbering):
- For the global receipt and the five in-scope desk receipts, a script verified for **every** recorded entry that the inode and link text still matched and that the only difference was `dev`, then rewrote `dev` to the current value. Entries that no longer existed on disk were left alone. Zero mismatches, so nothing foreign was adopted. Originals are in the backup dir.
- Receipt files were edited by hand-run script, not by Skillex. This is the one step outside the documented CLI surface.

**Follow-ups for the owner of the Mac setup:**
1. This will recur on any macOS event that renumbers the volume. Skillex should treat a `dev` mismatch with matching `ino` as the same entry (or key on volume UUID). The same drift hits every other receipt on the Mac, untouched here: `hello-subconscious-team-inbox` project roots, `mission-control`, `ipm-aai`, `space`, `Music Lab`, `damian-engineering-workflow`, and the `team-inbox` desk.
