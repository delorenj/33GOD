## 3. Design

Why leases miss it (source read at the pin, same as W6-1's verifier): the collectors (`collect_generations`, `collect_runtime_generations`, `collect_orphan_install_states`) remove an unselected generation older than a day when `leases_held()` is false. A lease is a flock taken by a Hermes reader. An MCP server started from `…/environments/<id>/venv/bin/python`, or a launchd job whose `PATH` names that `venv/bin`, holds none.

Call sites covered, all through the three collectors (one shared guard, so no route is left out): `collect_superseded_generations` (venv_sync.py:123 and :677 after every `pm.sync_venv`, `_update_takeover.py:59`, `update_completion.py:355`, `pm/recovery.py:63`), `hermes pm gc` (`pm/cli.py:584-592`), and the startup worktree pruner (`worktree_ops.py:1138`, orphan states).

New sibling module `hermes_cli/runtime_state_users.py` (288 lines, stdlib only; repo convention `<stem>_<topic>.py`):

- `unused(candidates, kind=...)` returns the candidates nothing uses, in order. It logs `kept <kind> <path>: pid N (comm): <what>` at INFO per kept candidate. It returns `[]` and logs a WARNING when the probe returns None, or when it raises (any `Exception`): reclaiming space must not fail an update that has already committed (`collect_superseded_generations` only catches OSError/ValueError, and my first run hit exactly that, see 5.4).
- `users_of(candidates)` returns `{path: reason}` or None. Process users first, then `_unit_users` (setdefault) for launchd agents (`<real home>/Library/LaunchAgents/*.plist`) and systemd user units with drop-ins (`$XDG_CONFIG_HOME` or `<real home>/.config` `/systemd/user`), read as raw bytes, loaded or not, regular files only (no FIFO hang under the install lock). The account home comes from `hermes_constants.get_real_home()`, not a profile `HOME`.
- Matching is plain byte containment of each candidate's absolute and realpath spelling (`/tmp` vs `/private/tmp` on macOS) in a process's views. Exact here because generations, PM runtime generations and install states are all fixed-width ids.
- One probe per OS family:
  - Linux `/proc`: per pid `exe`, `cwd`, fd links, `maps`, `cmdline`, `environ`. A per-process OSError just skips that view (other users' processes expose only argv).
  - macOS/BSD: `/usr/sbin/lsof -n -P -w -F pcfn` plus `/bin/ps -A -ww -E -o pid= -o command=`, by absolute path (a `PATH` entry can shadow them and a launchd `PATH` lacks `/usr/sbin`), 15 s timeout, rc must be 0. lsof reports the interpreter a venv symlink resolves to, so only `ps` argv names the venv.
  - Windows: psutil (exe, cwd, open_files, memory_maps, cmdline, environ) when importable.
- Self-witness rule: a listing counts only if it includes the probing process itself (its own argv on Linux, its own pid in both macOS listings, argv in psutil). An empty or hidden `/proc` (hidepid, sandbox) therefore reads as failure, never as "nothing runs".

Deliberate deviation from the task wording, "psutil if already a dependency, else lsof on Darwin and /proc on Linux": psutil is a core dependency (`psutil==7.2.2`) but the update tail runs the collector from an `-I -S` bootstrap interpreter where it is not importable, and psutil on macOS has no `memory_maps` (so a mmapped-only user, like the `txt` `.so` lines that show PID 10788 on the Mac, would be missed). Native probes first gives ONE answer per host whichever interpreter collects; psutil remains the Windows path and has its own test.

Wiring (diff stat `8 files changed, 561 insertions(+), 11 deletions(-)`): `collect_generations` and `collect_runtime_generations` collect their candidates first, then `for generation in unused(candidates, kind=...): rmtree`. `collect_orphan_install_states` probes the orphan list once before the per-state lock re-check. Docstrings and docs updated (`website/docs/reference/package-management.md` GC paragraph and the `pm gc` row, `website/docs/developer-guide/pm-audit-status.md`). zh-Hans translations untouched.
