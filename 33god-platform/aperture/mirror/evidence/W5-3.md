## 2. Manifest (as committed and as registered)

```toml
[candybar]
name = "mac-canary"
description = "Damian's Mac Candybar clock liveness canary"
tags = ["mac", "canary"]
schedule = "5 * * * *"
timezone = "America/New_York"
enabled = false

[candybar.runner]
kind = "exec"
argv = ["/bin/sh", "-c", "printf '%s %s\\n' \"$(/bin/date '+%Y-%m-%dT%H:%M:%S%z')\" \"$(/bin/hostname)\" >> \"$HOME/.local/state/33god/candybar-canary.log\""]
timeout_s = 30
```

Placement: `deploy/smoke/<kind>/candybar.toml` is the repo's documented home for canary manifests (README line 91, `deploy/README.md` lines 176 and 251; `candybar register deploy/smoke/<kind>`). It is not under `deploy/migration/manifests/` (ledger-driven, autosync-watched) and not a `.candybars/` directory, so neither autosync nor a project `candybar register` run on big-chungus can discover it by accident: `autosync.py` only watches explicitly configured project and legacy paths, and `steward/context.py` only `rglob`s `deploy/**/candybar.toml` to look up a manifest for a name it already has. The name and tag both contain `canary`, which `steward/context.py` lists among its `PROTECTED_NAMES` and `PROTECTED_TAGS` (the driver read the constants, not the steward's behaviour on a Mac registry). `HOME` is an explicit key in the executor plist's `EnvironmentVariables` (value `/Users/hellosubconscious`, read by the driver with `plutil -extract`), so the host-neutral `$HOME` path resolves to `/Users/hellosubconscious`; no `/Users/...` literal is in the file. The schedule is minute 5 of every hour so the first scheduled fire fell 4 minutes after `resume`, which made the real-fire proof possible inside one session; it is still hourly.

Why `enabled = false` in a job that ends up enabled: `enabled` is never synced from a manifest (candybar skill, step 3). It was registered disabled, proven by a manual run, then enabled with `candybar resume mac-canary`, exactly the skill's order.

## 8. Findings

1. **No CPU or memory metering on the Mac.** `candybar show` and `ls` report the canary as `○ unmeasured`; each run row has `MEM 0B CPU 0.00`, and the cost notes say `CPU/memory not metered for any run in the window`. This is the expected consequence of `CANDYBAR_CGROUP_ROOT=''` (the executor meters through cgroups, which Darwin lacks), so `candybar cost` cannot rank Mac jobs and the cost tiers will stay hollow for every Mac job. Runs and exit codes are recorded correctly. Whether a Darwin meter (rusage of the child) is worth building is an upstream question, not a W5-3 defect.
2. **The Mac cannot land code upstream.** Its GitHub identity (`DamiMiller`) has read-only access to `delorenj/candybar`, and the Mac cannot ssh to big-chungus. Any Mac-lane artifact that must be tracked (this manifest, W5-4's, W9-4's) needs a big-chungus driver commit, as here. Not a bug; it constrains how W5-4 and W9-4 deliver their manifests.
3. **The whole clock path works on Darwin end to end**: heartbeat tick (`tick:29908205`, published by the container) to dispatcher, NATS durable `candybar-executor-invoke`, host executor, `/bin/sh` child, registry terminal row. The first scheduled invocation started 66 ms after the minute boundary (14:05:00.066Z) and finished in 28 ms.
