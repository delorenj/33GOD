## Issues

1. **MEDIUM - the NATS readiness gate is a no-op, and the worker's report says otherwise.**
   `start-hook-hub.sh` loops `while ! perl -e 'alarm 4; exec @ARGV' /opt/homebrew/bin/nats --server nats://127.0.0.1:4222 rtt`.
   I ran the exact same command against a dead port on the Mac: nats v0.5.1 prints `failed` / `no servers available` and **exits 0**.
   So the loop never waits, and the hub starts immediately whether or not NATS is up.
   The worker's retry test used a stub `fake-nats` script that exits 1, so it never exercised the real CLI's exit code.
   The report's "gates startup on `nats rtt` and retries" is wrong.
   Severity is bounded. `hub.py` has no NATS connect at start (`transport_error` only covers a missing socket) and the publisher is a per-event handler.
   After a reboot the hub should start fine before Colima and NATS are up.
   Events handled while NATS is down would fail to publish, and the observation outbox retries. That is inferred from the source and was not exercised live.
   The PLAN asked for a real gate. Fix: replace the probe with one whose exit code is honest:
   `/usr/bin/nc -z -w 2 127.0.0.1 4222` (exit 1 dead, 0 live, measured), or `nats --server nats://127.0.0.1:4222 server check connection` (exit 2 dead, 0 live, measured).
   Edit the wrapper only. A new hub process is needed to pick it up, and that restart belongs to the W2-3 owner.
   I did not make the change.
2. **MEDIUM - the live service depends on a dated scratch directory.**
   `ProgramArguments` runs `~/33god-migration/2026-11-10/w2-3/start-hook-hub.sh`, which execs `.../w2-3/venv/bin/python`.
   The earlier (superseded) rollback text in `W2-3.md` says `rm -rf` that directory, and a routine migration-scratch cleanup would take hook-hub down on its next restart.
