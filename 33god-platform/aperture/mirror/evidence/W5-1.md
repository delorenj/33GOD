## 2. Darwin live-policy collector (`src/candybar/scheduling_policy.py`)

`collect()` switches on `sys.platform`. On Darwin the inventory sources are `registry`, `launchd`, `crontab`, `hermes` and the inventory carries `"platform": "darwin"`; `audit()` picks the required-source set from that key (no key means Linux, unchanged). `uv run candybar doctor --repo . --live --json` therefore audits launchd on the Mac:

- Plist scan: `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`. `StartInterval` and `StartCalendarInterval` are the clock keys. `RunAtLoad`, `KeepAlive`, `ThrottleInterval`, `WatchPaths` are supervision or events, never flagged. Duplicate labels union their clocks; `Disabled` and the `print-disabled` override are honoured. A malformed plist or a missing `Label` makes the source `unknown` (exit 2), never a silent skip. `ProgramArguments`/`EnvironmentVariables` are never read into rows.
- Domains: `launchctl print gui/<uid>` and `user/<uid>` (`services = { PID Status Label }` block) plus `print-disabled`. Loaded labels with no plist and not `com.apple.*`, `application.*`, `0x*`, `[`, `UIKitApplication:` are probed with `launchctl print <domain>/<label>` (`run interval = N seconds`, `com.apple.launchd.calendarinterval`). "Could not find domain" means no GUI session and is tolerated. Any other launchctl failure, or an output shape the parser does not know, is `unknown`. Only the verbs `print` and `print-disabled` are ever run (tested, including a static check that no mutating verb appears in the module).
- Cron: `crontab -l` for the user; a missing `/etc/cron.d` and `/etc/crontab` are tolerated on macOS only (`tolerate_missing_cron_d`); on Linux they remain an unreadable inventory.
- Rows: `{"id": "launchd:<label>", "label", "clocks", "active", "domains"}`. An active launchd clock is a bypass with the exact id `launchd:<label>` and can be exempted only by an exact-id record in `deploy/scheduling-policy.json`. Findings are observations; nothing is disabled.

## 6. Problem found along the way: the test suite blocks on a shared flock

The first baseline run stalled at about 10% (around the autosync tests). `src/candybar/autosync.py::_reconcile_lock` takes `fcntl.flock(LOCK_EX)` on `$XDG_RUNTIME_DIR/candybar/sync-<hash(api_url)>.lock`, a process-wide, host-wide lock. `/proc/locks` showed 22 processes queued on that one inode (`/run/user/1000/candybar/sync-46ac0e68….lock`): about 20 of Jarad's live `candybar watch <repo> --if-present` processes plus my pytest. A test that reconciles therefore waits on whatever the live watchers hold. I did not touch any watcher. I killed only my own hung pytest (PIDs 3176712/3176764 and its duplicate) and reran both suites with `XDG_RUNTIME_DIR=$(mktemp -d)`; both then finish in about 112 s. Anyone running candybar's tests on big-chungus without that override can hang for the same reason. Not fixed here (out of W5-1 scope; see findings).
