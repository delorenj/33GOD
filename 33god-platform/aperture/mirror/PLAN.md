## 1. Deploy-mode decision

**DECISION: CONFIRM the orchestrator's proposed rule — hybrid, mirroring Jarad's topology — with the rationale restated and an evidence standard attached.**

The draft justified the hybrid by arguing against Docker Desktop's VM capacity. That argued against Docker Desktop, not against containers — this plan keeps a VM (Colima). The load-bearing rationale, restated:

1. **A container VM is mandatory regardless.** Decision 3 commits to migrating Damian's own five Docker stacks (Plane, opensign, pjangler registry PG, n8n-foundation, onepassword-redis). That is his data and his choice; no native port of those stacks is on the table. Given a VM must exist, compose parity with big-chungus for the shared 33GOD services (NATS, Dapr, Candystore, Candybar control plane, Hindsight server) costs almost nothing and keeps the two peers debuggable as one system.
2. **Full containerization fails on host coupling.** hook-hub, Hermes, flume, pj, waxd and the report tooling spawn host CLIs, read host files, and sit on the agent hot path; containerizing them buys bind-mount friction and nothing else.
3. **Full native fails on divergence.** NATS/pgvector/Dapr/Postgres as native services would be a bespoke maintenance burden with zero upside. (Every workload does have a clean Darwin path — nats-server via brew, postgresql@17+pgvector via brew, candystore/turn-enricher via uv, daprd ships darwin/arm64 — so this is a deliberate trade-off, not a forced one. It is accepted because of point 1.)
4. **Coupling acknowledged:** if W4-3 resolves to option (b) — Damian takes a seat on Jarad's `plane.delo.sh` instead of keeping his self-hosted Plane — the largest single container workload (Plane's 12 containers) disappears and the container requirement shrinks to the 33GOD shared services plus opensign/n8n-foundation/onepassword-redis. The deploy-mode decision stands either way, but the board decision is not independent of it.

**Evidence standard (from review):** big-chungus topology is the starting point, not proven fact for any component. Before each component lands, its parity must be established with per-component evidence: arm64 image manifest, host-integration needs, launchd lifecycle, networking, data migration and recovery. The Mac survey was Mac-side only; source-side image/topology parity is an execution prerequisite checked per wave, not an assumption.

### The rule (one sentence, applicable per component)

> **Compose where big-chungus uses compose (third-party servers with a port + a volume); source checkout in `~/code` + mise + a launchd LaunchAgent where big-chungus uses systemd user units (our code, or anything touching host CLIs, hooks, files, audio, or GPU); drop what is Linux-only.**

Corollaries:

- launchd units: `user/501` domain (the domain the Mac's working agents already use; `gui/501` prints fail for them), `RunAtLoad` + `KeepAlive` only, absolute paths, explicit `PATH` and `HOME`, explicit log destinations, dependency-readiness checks (a `KeepAlive` loop against a missing dependency is a thrash, not supervision). **Never** `StartInterval`/`StartCalendarInterval` — Candybar is the only clock.
- No systemd anything. Linux-only features behind flags (`BLOODBANK_ASM=false`, `CANDYBAR_CGROUP_ROOT=""`) get set, not ported.
- The container runtime on the Mac is **Colima** (vz + virtiofs + rosetta, ~12 CPU / 32 GiB / 200 GiB, launchd-managed), not Docker Desktop.
