# I-9 native-message owner refinement

## Why

Move the accepted pane-bound crank route from architecture agreement to one useful
owner contract without guessing a Fleet PM, duplicating component tracking or
pretending Claude input is enabled. This parent-authored package awaits real
owner adoption; coordination designation and request publication are not adoption.

## Capabilities

- **CAP-1**
  - **intent:** Route the planning request through the actual enrolled coordinator with an explicit authority boundary.
  - **success:** Repo/role/board/fleet evidence agrees; exactly one authorized supported planning request yields an actual accepted/blocked response or evidenced transport blocker, never invented acceptance.
- **CAP-2**
  - **intent:** Hermes Fleet can refine the smallest native-message capability contract without acquiring agent facts or crank policy.
  - **success:** G1 schema compatibility, G2 exact incarnation protection through asynchronous ingress and G3 independent receiving-input acceptance each have binary cases, evidence requirements, accountable owners and an owner-supplied runnable validation manifest prerequisite; unsupported remains zero send.
- **CAP-3**
  - **intent:** Resume contract planning using existing owner work, explicit dependencies and the accepted catalog ownership.
  - **success:** One owner per planning item, typed dependency edges, current BB-32/BB-33/PJAN-202 references, an exact unapplied catalog delta and a readiness verdict separating planning adoption from implementation/input enablement.

## Constraints

- Inherit final I-9 AD-1–12. Only pane-bound local-Linux Claude native messaging is a candidate; no terminal fallback. Claude is not certified support.
- Fleet owns narrow `agent.message`; ASM facts, terminal-driver topology/actions, crank opt-in/admission/attempts and pj integration remain separate.
- The user-supplied delegated pjangler-pm disposition designates existing `flume-pm`/FLUME coordination-only for this Fleet-owned planning contract. It transfers no contract/mutation ownership and selects no code home.
- Exactly one planning-only request is authorized through the verified existing transport; it has been published. No blind resend on uncertainty. A transport receipt is not planning acceptance or API readiness.
- Crank retains uninterrupted exclusion through final endpoint/session validation, last-point binding/revocation/eligibility revalidation and irreversible submission. Pre-point revocation prevents new submission; after possible submission no retraction or continuous-idleness promise.
- Unknown fences the receiving incarnation across re-opt-in/new binding/takeover. Clear only corroborated input acceptance without replay or terminal nonacceptance ruling out later release; silence/timeout/held is not reconciliation. No universal exactly-once claim.
- All three native gates block enablement/proof. Independent receiving-input evidence is required, not model consumption/task completion. Missing wrapper alone does not negate architecture agreement.
- Beyond that single planning turn: no owner board mutation, code workers, implementation, native proof input, service/clock, spend, cap change, Git publication, merges or deployment. No stories or sprint-status generation in this parent package.

## Non-goals

- New features, headless/cross-pane delivery, session rotation/restart recovery, universal messaging or another detection/input/runtime stack.
- Transferring Fleet authority to Flume; creating a board, PM, actor, ticket or repository.
- Replacing owner backlogs, rerunning prior deliveries or treating a published request as accepted handoff.

## Success signal

The verified coordinator returns bounded accepted/blocked planning findings with
actual source/contract/capability and G1–G3 manifest or precise unsupported evidence.
Readiness incorporates that response without promoting implementation/input or
behavioral gates. Catalog changes remain an unapplied proposal.
