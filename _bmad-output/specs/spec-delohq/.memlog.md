- (direction) Adopt the finalized DeloHQ architecture spine as the implementation-facing spec while preserving the PRD and spine as downstream companions.
- (decision) DeloHQ remains the executive experience hosted by Holocene /hq; v1 creates no separate DeloHQ repository, service, API, database, event stream, or workforce registry.
- (decision) Flume owns workforce identity, hierarchy, delegation, escalation, and policy; PJangler owns project identity; Krebs and Pilot own ticket lifecycle; Bloodbank and Candystore own event transport and history; Hermes owns runtime execution and receipts.
- (decision) All browser data crosses authenticated /hq/api routes and one shared delohq-contracts registry; the browser never reads host files, event stores, runtime controls, Flume stores, or internal APIs directly.
- (decision) Canonical opaque identifiers, source and evidence metadata, timestamps, freshness, and explicit Unknown or error states survive every projection; display names and usernames are labels only.
- (decision) Now, Executive Inbox, and history are composed from canonical evidence with shared item identity, grouping, attention precedence, and receipt normalization; surfaces may filter or order but may not reclassify independently.
- (decision) Consequential operations are named, typed, allowlisted commands with originating context, actor context, idempotency, correlation, canonical-system transitions, and durable normalized receipts; HTTP acceptance is never completion.
- (decision) Every public /hq request verifies Telegram Mini App initData and derives actor context; the split Traefik, holocene-web, and holocene-api deployment degrades explicitly and never fabricates healthy or completed state.
- (decision) CAP-1 covers a Flume-backed Company projection; success is a coherent hierarchy and posture view using one workforce snapshot, canonical identity, and explicit freshness or Unknown state.
- (decision) CAP-2 covers meaningful Now movement; success is grouped canonical evidence with exact context links and no inference of progress from raw volume, polling, absence, or empty results.
- (decision) CAP-3 covers Executive Inbox attention and decisions; success is shared human-consequence classification with evidence, priority, and preserved entry context.
- (decision) CAP-4 covers Agent Office context; success is a canonical Employee view joining role, current work, project, runtime, and intervention paths without inventing ownership.
- (decision) CAP-5 covers bounded actions; success is explicit confirmation of a named capability dispatching only to its owning canonical system with actor, target, idempotency, and correlation.
- (decision) CAP-6 covers Action Receipt tracking; success is a durable receipt that preserves source state and evidence while rendering accepted, in_progress, completed, failed, expired, rejected, or unknown accurately.
- (decision) CAP-7 covers Telegram entry and conversation handoff; success is a verified context-preserving path from /hq to the owning conversation or canonical system.
- (decision) CAP-8 covers truthful projection envelopes; success is every Company, Now, Inbox, Office, action, and receipt response carrying schema, source, generation, observation, freshness, and evidence or error information.
- (decision) CAP-9 covers shared contracts; success is adapters, routes, views, and contract tests consuming the one versioned delohq-contracts registry and migrating through explicit versions.
- (constraint) The first Flume transport, numeric freshness budgets, initial action catalog, current /hq capability migration, and Company Memory evidence policy remain unresolved and must be decided before their dependent implementation slices.
- (constraint) The declared pnpm 10 and Node 22 Compose toolchain must be made executable before implementation evidence relies on package-manager commands; the current Node 26.5 host shim failure is a platform handoff, not a reason to invent a second stack.
- (assumption) Assume the approved DeloHQ name remains the executive-surface name; naming does not imply a separate deployable product boundary.
- (question) What max age makes each Company, Now, Inbox, and Agent Office projection stale or Unknown?
- (question) Which bounded Actions and receipt providers are in the first release beyond approve, reject, and acknowledge?
- (question) Which supported Flume read surface supplies the workforce projection, and how is the current org.yaml presentation overlay retired?
- (question) Which current /hq controls and capabilities remain, change, or retire under the DeloHQ navigation model?
- (question) Which Hindsight summaries can be shown in Agent Office without exposing raw private runtime memory?
