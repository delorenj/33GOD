## Classification and decision

**Overlapping purpose; older root scaffold effectively superseded for managed fleet roles, with legacy output still extant.** Both generators start a repository-scoped Hermes role, create an ignored runtime path and a launcher/provisioning surface. They are **not equivalent implementations**: root emits a plain `agents/<name>` tree and hardcodes an old `/home/delorenj/code/hermes-agent/.venv/bin/hermes` default plus Ollama/model/TTS defaults ([root installer:98-143](../../templates/hermes-agent-repo/install.sh)); the canonical Copier source emits `agents/hermes/<role>` with role manifest, SOUL, lifecycle/provisioning scripts, profile/registry integration and host-configurable fleet paths ([template README:43-64,179-194](https://github.com/delorenj/hermes-agent-template/blob/c738f69/README.md#L43-L64), [copier.yml:11-25](https://github.com/delorenj/hermes-agent-template/blob/c738f69/copier.yml#L11-L25)). The older root script promises repo-local runtime isolation only; it does not implement current host-level single gateway/Skillex policy. The tracked older-style Bloodbank launcher is not evidence of a currently running legacy runtime.

**Recommendation (decision basis: ticket's Pillar 3, “Build LEGO, Not Statues”; one owner per atom and the [Director Rule:29-51](director-rule-plan.md)):** make `hermes-agent-template` the *single authoritative role-generation contract*; Flume remains the workforce hire/render consumer and its pinned gitlink remains a dependency, not a fork. Retain the root script **unchanged during this spike**. Root 33GOD should own only the platform-level explanation/deprecation pointer and seam acceptance; after a bounded owner audit of known legacy-style outputs and any external callers, the 33GOD PM can ask the Hermes Fleet/template owner and Flume PM to agree whether to archive/remove the redundant root installer or preserve a documented standalone, non-fleet use case. Do not silently redirect root installs to Copier: Copier executes host/board/registry work and is not behaviorally interchangeable. The Fleet/template owner handles any generator compatibility or retirement change; Flume PM handles hire/consumer resolution and pin validation; owning child PMs handle legacy role migrations if requested. No profile or generated output is changed here.

**Adjacent work is not this spike:** [I-4 / 33GOD-81](initiatives.md#i-4-repository-aware-pm-skills-and-a-33god-bmad-integration-companion) already delegates repository-aware PM skill discovery to Flume, canonical BMAD companion packaging to Skillex, and installer consumption to PJangler ([initiatives.md:256-304](initiatives.md)); don't insert a skill pack or duplicate installer into either template. [33GOD-59](https://plane.delo.sh/33god/browse/33GOD-59/) owns retiring global per-CLI hook fanout in favor of Bloodbank `services/agent-hooks/hooks.master.json` and deciding the synchronous Hindsight exception; no hook edit or claim of hook retirement is made here. These are different authority seams from role generation. Canonical Copier has its own per-agent unit/heartbeat *cleanup* ([`70-systemd.sh:1-17`](https://github.com/delorenj/hermes-agent-template/blob/c738f69/template/.scripts/70-systemd.sh#L1-L17)); that is not an implementation of 33GOD-59's global CLI-hook retirement.
