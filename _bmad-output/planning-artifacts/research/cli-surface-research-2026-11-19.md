## AWS mechanism
 The aws command is a generic interpreter for a data contract. It is not 200+ CLIs glued together.

1. Contract. Every service team publishes a machine-readable API model. In the CLI this is botocore's `data/<service>/<api-version>/service-2.json`, plus `paginators-1.json`, `waiters-2.json` and `endpoint-rule-set-1.json`. A model lists operations (HTTP method and URI, input shape, output shape, errors), a shape graph (structure, list, map, string with required members and locationName), and metadata (protocol such as json, rest-xml, ec2 or query; signatureVersion/auth; endpointPrefix; serviceId). Paginators and waiters are declarative. A paginator names input_token, output_token, limit_key and result_key. A waiter gives a polling operation, delay, maxAttempts, and acceptors that are JMESPath matchers mapped to success, failure or retry states. The same Smithy-derived models drive every AWS SDK, so the CLI is one generated consumer among many.

2. Discovery by directory scan. `Session.get_available_services()` calls `Loader.list_available_services('service-2')`, which traverses the data search path (botocore/session.py:581-587, loaders.py:260). The search path is `~/.aws/models` first, then the built-in `botocore/data`, plus `AWS_DATA_PATH` (loaders.py:217-243). A service is a directory containing a model file. There is no registry of services.

3. Runtime command generation. `CLIDriver._build_builtin_commands` makes one `ServiceCommand` per discovered service (clidriver.py:493-502). `ServiceCommand._create_command_table` makes one `ServiceOperation` per `service_model.operation_names`, with the CLI name `xform_name(op, '-')`, so DescribeInstances becomes describe-instances (clidriver.py:768-793). `ServiceOperation._create_argument_table` walks `input_shape.members` and builds one CLI argument per member. Shape type picks the argument class through `ARG_TYPES = {list: ListArgument, boolean: BooleanArgument}`, defaulting to `CLIArgument` (clidriver.py:825-829, 1046-1085). Required members become required flags, and idempotency tokens are made optional. The `--help` text comes from the model's documentation field.

4. Invocation. `ServiceOperation.__call__` parses args, calls `_build_call_parameters` to produce kwargs, then `CLIOperationCaller.invoke` runs `session.create_client(service, region, endpoint_url, verify)`. It then calls `client.<snake_op>(**params)` or `client.get_paginator(...).paginate(**params)` (clidriver.py:920-1004, 1097-1158). botocore's `ClientCreator._create_methods` builds every client method from the same model (client.py:412-447). `_make_api_call` then does the serialize, sign, send, retry and parse steps for the model's protocol (client.py:830+).

5. Shared core. All services get the same behaviour from one runtime, because it sits above the model.
- Credentials: a single provider chain, with env, assume-role, profile providers (SSO, web identity, shared credentials file, process), then container and IMDS (credentials.py:81-150).
- Config: `~/.aws/config` profiles and sso-sessions, and the global flags `--profile`, `--region`, `--output`, `--query`, `--endpoint-url`, `--no-paginate`, `--cli-auto-prompt`, which are declared once in `data/cli.json`.
- Output: json, text, table, yaml and yaml-stream. `--query` is JMESPath, applied in `formatter.py:50-52`.
- Retries: standard and adaptive modes (client.py:234-262).
- Pagination and waiters: `aws <svc> wait <state>` is generated from `waiters-2.json` (customizations/waiters.py:24-45, 211-225).
- Input helpers: `--cli-input-json/yaml` and `--generate-cli-skeleton` are injected into every operation's argument table via the `building-argument-table` event (customizations/cliinput.py:23-41, generatecliskeleton.py:27-28).
- Completion and auto-prompt: a SQLite index (`data/ac.index`) is generated from the clidriver at build time (autocomplete/generator.py:22-76). `aws_completer` and `--cli-auto-prompt` read it instead of booting the whole model tree.

6. Customization seam: events. botocore's HierarchicalEmitter fires named events during command building and calling: `building-command-table.<svc>`, `building-argument-table.<svc>.<op>`, `operation-args-parsed`, `calling-command`, `after-call`, `doc-*`. Hand-written code attaches to them. v2 centralizes this in `PLUGIN_REGISTRY` (about 230 event-pattern to (module, fn) entries) and `MAIN_COMMAND_TABLE_OPS`, loaded lazily by `LazyInitEmitter` (handlers_registry.py:36 and 885+, lazy_emitter.py). Examples:
- `aws s3` is a hand-written `BasicCommand` that renames the generated `s3` to `s3api` and then injects the high-level s3 command (customizations/s3/s3.py:30-68).
- `aws ecr get-login-password` is injected into the generated ecr command table (customizations/ecr.py:20-47).
- `aws ssm start-session` replaces the generated operation with a subclass whose caller makes the model-driven StartSession API call and then subprocesses the external `session-manager-plugin` binary (customizations/sessionmanager.py:46-62, 138-215).
So the shape is generated 1:1 by default, and handwritten layers sit only where UX needs more than a raw API call.

7. Plugins. In v1 and v2, `[plugins]` in `~/.aws/config` with `cli_legacy_plugin_path` imports Python modules and calls `awscli_initialize(event_hooks)` (plugin.py:36-60, clidriver.py:131-134). AWS calls v2 plugin support "completely provisional" with no stability guarantee (cliv2-migration-changes docs). The stable extension mechanism is data, not code. Dropping a `service-2.json` into `~/.aws/models/<svc>/<ver>/` or `AWS_DATA_PATH` creates a new `aws <svc>` command. I verified this locally (see aws_facts).

## not unified
 AWS is unified at the API layer and not at the workflow layer.

Unified: the `aws <service> <operation>` surface for about 426 services and 18.8k operations. It is generated 1:1 from service models, plus a thin set of hand-written commands (s3, configure, ecr get-login-password, ddb, logs tail, history, wizards) injected through the event system into the same binary.

Separate binaries, each owning a distinct workflow, language and release cadence:
- SAM CLI (`sam`, Python, built on boto3/botocore). It does build, local invoke and deploy of serverless apps via CloudFormation transforms.
- CDK Toolkit (`cdk`, TypeScript, built on AWS SDK JS v3). It does IaC synth and deploy.
- Amplify CLI (TypeScript). It does full-stack app scaffolding.
- EB CLI (`eb`, Python on botocore, bundling its own copy of the botocore data). It does Elastic Beanstalk app lifecycle.
- Copilot CLI (Go, now end-of-support). It did container app lifecycle.
- session-manager-plugin (Go, invoked by `aws ssm start-session`). It is a native-protocol websocket client for interactive terminal and port-forward sessions. The CLI could not reasonably embed it. It is a sidecar behind a tiny argv/env contract.

Why these are separate: they are opinionated, stateful workflows with their own project files (template.yaml, cdk.json, .elasticbeanstalk, amplify/), local runtimes (Docker for sam local), and different release cadences and language ecosystems. A service API model can describe `ec2 run-instances` but not `sam build`. What they share is the lower layer: the AWS SDKs or botocore, the shared config/credentials files and credential chain, and the Region and endpoint rules. AWS treats the user-facing umbrella as the API surface, not as a bag of every tool.

## lessons
- Essential to AWS's unification: a versioned, machine-readable contract owned by each component's team (service-2.json plus paginators-1.json and waiters-2.json, and endpoint rule sets), and one generic interpreter. The CLI generates its commands, flags and help text from the contract. Nothing about the umbrella is hand-curated per service. The local drop-in experiment proves it: a 14-line JSON file at ~/.aws/models/pipe33/... made a full `aws pipe33 start-run` with help, skeleton, --query and --output, with no code.
- Essential: a shared config and credentials spec. The credential chain, profiles, Region and endpoint resolution, retry, output and JMESPath semantics are written once and reused by every SDK and by tools like CDK, SAM and EB. The AWS SDKs and Tools Reference Guide documents it as a cross-language spec. That is why SAM (Python) and CDK (TypeScript) feel unified with `aws` although they are separate binaries.
- Essential: an extension seam of named events and a thin hand-written layer. Almost everything is generated 1:1. The few UX commands (s3 cp/sync, configure, ecr get-login-password, ssm start-session) are customizations attached to events. Even the sidecar is a tiny argv/env contract (session-manager-plugin). Generated by default, hand-written by exception, and the exceptions stay in one registry (handlers_registry.py).
- Essential: a version of the API contract that outlives the binary. The same models feed Smithy codegen for the JS, Go and Rust SDKs, and botocore for Python. The contract is what AWS invests in, and the CLI is only one consumer.
- Incidental: the monolithic Python binary. v2 is a frozen exe with an embedded interpreter, built that way for distribution (no Python needed on the user's machine), not for unification. Evidence that the binary is not what unifies AWS: SAM, EB, CDK, Amplify, Copilot and session-manager-plugin are written in Python, TypeScript and Go, and still share the contract and config. Its plugin system is a provisional v1 Python import hook that AWS tells users not to rely on.
- Incidental: in-process dispatch and one cold-start tree. AWS needs a prebuilt SQLite completion index (ac.index) and a LazyInitEmitter just to make the monolith start fast. A PATH-dispatch umbrella does not pay that cost.
- AWS's own seams are not uniform: the generated surface is unified, while workflow tools are separate. This matches the 33GOD split. Unify what has a stable API contract (bloodbank, candybar, candystore, pilot, pjangler, hindsight, skillex), and let workflow glue (build, release, runtime ops) stay separate and use the shared config.
- Recommendation, my judgment and not a fact from the sources: follow AWS's contract, not AWS's architecture. Do not build a monolithic `33god` binary. The 33GOD CLIs on this machine are already polyglot: pj, px/pilot, flume and skillex are Node (pj -> @delorenj/pjangler/dist/index.js, px -> 33GOD/pilot/bin/pilot.js, flume -> flume-hr/dist/index.js); candybar, candystore and bloodbank are Python (uv tools and bin/bb); hindsight is a native ELF; waybill and wax are shell. A single-language monolith or an in-process plugin system (az, oclif, gcloud) would force a rewrite. The best-fitting comparator is Docker CLI plugins (the metadata handshake) on top of git and kubectl-style PATH dispatch. Concretely, build a thin umbrella (for example `33` or `gz`, as thin as `git`) that scans PATH or a registry such as components.yaml for `33god-<name>` executables and execs them, requiring each CLI to answer `--describe` or a `33god-cli-metadata` call with JSON (name, version, commands, JSON Schema for args and outputs, exit-code table). I did not read components.yaml or features.toml for this task.
- Agent-first lesson, same recommendation: the biggest win is not the shared `aws` word but the shared contract that agents can read without running anything. Mirror AWS's pattern with (a) a per-component machine-readable command schema (JSON Schema or OpenAPI-like) from which each polyglot CLI's flags and help can be generated, (b) one shared output contract (`--output json|text|yaml`, `--query` JMESPath, stable exit codes, `--generate-cli-skeleton`-style input skeletons, `--cli-input-json`), and (c) one shared config and credential spec (profiles, op:// references, Bloodbank endpoint). That is how an `aws` call is predictable to an agent, and a PATH-dispatch umbrella plus a contract gets it for a solo maintainer without a framework.
- On mise: nothing in the AWS evidence argues that task runners should drive a pipeline. AWS's unified layer is the typed API contract, and the workflow tools sit on top. The evidence supports replacing mise tasks with real per-component CLIs behind a thin umbrella. It does not say anything about whether mise stays for tool and runtime installation, which is a separate layer.
- Caveats on evidence: the awscli Python source is compiled into the exe, so I cited the aws/aws-cli v2 branch at commit e1cb1f84 (2026-11-19), and line numbers may differ slightly from the installed 2.35.24. The claim that botocore's service-2.json is derived from Smithy is inferred (medium confidence). I also created demo files only under /tmp/aws33demo and /tmp/awssrc (source downloads for reading), and ran `gcloud components update`, which refused. I changed no repo files, configs or branches.

## DESIGN verdict
 Partly. Copy AWS's pattern but not its architecture. AWS gets one `aws` command over 426 services because each service ships a machine-readable model (botocore service-2.json, found by scanning a directory). One generic interpreter turns those models into commands, flags and help at runtime, and config, credentials and output are written once (clidriver.py:768-793, 1046-1085; credentials.py:81-150; data/cli.json). AWS's workflow tools (sam, cdk, eb, session-manager-plugin) stay separate Python, TypeScript and Go binaries that share only that config. Every 33GOD CLI is a workflow tool of that second kind, written in mixed languages (Node commander, Node parseArgs, Python Typer/argparse, Rust). Keep mise for runtimes, env, enter-hooks and per-repo build/test, and move out only the cross-repo tasks and the tasks that are just aliases.

## risks
- Describe drifting from real behaviour. Mitigation: generate it from the parser objects (commander tree, click to_info_dict, argparse actions) and run `33god conform` in each component's test suite, the way px's surface.test.js already fails on drift.

- Latency. Node startup adds roughly 40-60ms to every agent call before execve hands off. Mitigation: the cached index means help and listing never spawn components. A hot path such as Candybar can still call the native binary directly, and the contract still applies there.
- process.execve is flagged experimental in Node; it exists in the installed v24.6.0. A Node upgrade could change its behaviour. Mitigation: a spawnSync({stdio:'inherit'}) fallback that forwards signals and passes exit codes through.
- Envelope migration breaking cross-CLI consumers, because pilot registry.js:61 and candystore projects.py:75 parse raw `pj list --json`. Mitigation: describe says envelope: raw and the umbrella wraps on its side. Change native shapes only after the consumers move.
- atlas.json going stale relative to components/*.yaml, so the umbrella resolves a wrong path. Mitigation: atlas check fails when it is stale, `33god ls` and `where` show the resolved path, and PATH is the fallback.
- External tools (hindsight, the hermes upstream fork) need hand-maintained describe files that drift on upgrade. Mitigation: describe records the version it was written against, and conform flags a mismatch.
- Hermes PATH shadowing is partly intentional: the per-PM launcher scopes HERMES_HOME to a profile. Pinning ~/.local/bin/hermes in the registry could hide that. The registry entry must say which one `33god hermes` means, perhaps with a --profile passthrough.
- The MCP projection works only in local stdio mode, because the hosted mcp.delo.sh container cannot run host binaries. Do not promise remote MCP coverage of the CLIs.
- A Bloodbank cli-runner makes CLIs remotely triggerable, and duplicate delivery can repeat a write. Mitigation: route only commands that declare idempotent:true, keyed on the command's idempotency_key, and build it only on request.
- Solo maintenance cost: two small helpers (Node and Python), one schema, and conform work across about 12 CLIs. Mitigation: conform in order of agent call frequency, and leave low-value tools at envelope: raw with umbrella wrapping.
- A name that starts with a digit cannot be a shell variable name. Mitigation: the GOD_ env prefix. The `god` alias could collide with a future tool, so keep `33god` as the canonical name in manifests and scripts.

## corrected verdict
 On how AWS does it, the design is correct. `aws` is one generic interpreter over per-service botocore models: 426 services and 18,797 operations, plus shared config, credentials and output, with hand-written customizations attached through named events. Workflow tools (sam, cdk, eb) stay outside it. `aws ssm start-session` already runs the separate session-manager-plugin binary from PATH, with no contract asked of it.

Should 33GOD follow the pattern? Follow AWS's contract idea, not its front door, and do not make a passthrough `33god` the canonical way to run things. In order:

1. Fix the real faults directly; this fits in a day and needs no umbrella:
   - symlink krebs into ~/.local/bin;
   - stop exporting the per-PM hermes launcher on the global PATH;
   - pin interpreters in launchers and Candybar argv (absolute node 24 / process.execPath), so `env -i`, systemd and cwd pins of node 20 or 22 cannot break skillex or krebs;
   - pin skillex in mise, and remove `pj skills` or make it exec PATH skillex.
2. Adopt the usage spec as the shared describe contract instead of inventing `33god.cli/1`. Each component answers `--usage-spec` through the existing exporters (@usage-spec/commander, usage-spec-typer/-click, argparse-usage, clap_usage), or ships a static .usage.kdl. That gives completion, markdown for hub skills (drift checked in `skillex skill lint` or each repo's tests) and `usage mcp` without new code. Upgrade usage 3.3.0 to 7.x first.
3. Standardise only what usage does not cover: one JSON envelope (a superset of skillex v2 that skillex already satisfies, with flume aliasing `schema` before dropping `schema_version`) and one exit-code table. Change components one at a time, starting with the CLIs agents call most, and keep `envelope: raw` plus consumers-first for pj.
4. Add a small `33god` only for discovery and health: `ls`, `where`, `versions`, `doctor --all`, `describe`, reading the registry and the usage specs. It could start as platform.py subcommands. Native binary names stay canonical in skills, guards and Candybar. If passthrough is added for Jarad, first teach native_clock_guard and the other argv guards to unwrap it.
5. Mise: keep tools, env, enter-hooks, build/test with depends, every deploy task, and mobile-deploy-hub's `mise run deploy`. Delete only true alias tasks with no depends, env or dir, and rewrite the docs that cite them in the same commit. Retire skills:sync with `skillex integrations retire-mise` and fix the generators.
6. Leave out the Bloodbank cli-runner and the mcp-hub `cli` domain until a real caller asks. The bus has a closed command vocabulary and signed actor envelopes, so neither can be a generic projection.
7. Add a features.toml `[candidate.*]` entry first, and check portability for the Mac peer.

Belsky level: every 33GOD component CLI is on PATH with a pinned runtime, describes itself in a standard spec, and speaks one envelope and one exit table. It is not a CLI platform with its own schema, conform framework and four projections. Corrected scores: the design's option 4 as written, 6/10; the usage-spec contract plus root-cause fixes plus a discovery-only front door, 8/10.
